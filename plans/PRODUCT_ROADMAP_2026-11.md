# 产品路线图：让工作台好用、可信、可交付（2026-11 起）

> 用途：作为后续若干轮执行计划的总纲。每一轮从这里挑一个里程碑，再写成具体的执行计划交给执行代理。
> 前置条件：先完成 `plans/EXECUTION_PLAN_2026-11_PHASE2.md`，也就是修回归、测试全绿、冒烟测试落地。地基不稳时，下面的任何事都不要开始。

## 1. 产品判断

**它是什么**：研究人员的作战概念推演工作台。核心价值链是：

> 输入设想 → 检索知识 → AI 起草 → 人工修订 → 一致性评估 / 红队审查 → 带出处的成果

**现在离"好用"差在哪**（来自代码与界面复核，尚未经用户访谈验证）：

| 维度 | 现状 | 用户感受 |
|---|---|---|
| 可信 | AI 生成内容基本不带出处；有 `evidenceRefs` 字段，但没有贯通 | "这段是 AI 编的，还是资料里有的？" |
| 可控 | 恢复点、撤销只在少数操作上有；刚修好的 R3 说明这一块很脆弱 | "点了一下，原来的图没了" |
| 可懂 | 六步主线、OV-1～OV-6c、OODA 都是专业术语，信息密度高；动效投入过多 | "下一步该干什么？" |
| 可靠 | 测试以静态字符串断言为主；没有真实浏览器回归；AI 不可用时的降级不清楚 | "上次能用，这次又坏了" |
| 可交付 | 报告导出可用，但不带引用，也不能回写知识库 | "成果没法直接拿去汇报或评审" |

**总原则**：先可信、可控，再好懂，最后才是好看。暂停一切新增动效和新的视图类型，直到里程碑 M3 完成。

## 2. 里程碑

### M0 地基（进行中）：`EXECUTION_PLAN_2026-11_PHASE2.md`

完成标准：
- `run-checks.mjs all` 全绿；
- `smoke-ui.mjs` 0 个未捕获异常；
- `check-refactor-wiring` 进入门槛。

### M1 可控：任何 AI 或批量操作都能撤回（约 1 轮）

1. **统一"变更事务"**：凡是会覆盖模型的操作，都走同一个 `applyWithRecoveryPoint(label, mutate)` 包装：先存快照，再变更，失败时回滚。
   - 覆盖的操作包括：应用 AI 候选、从规划重新生成、导入、快照恢复、批量删除。
   - 先在代码里列出所有调用点，逐个迁移。
2. **全局撤销**：顶栏提供"撤销上一步（带操作名）"，基于上面的事务记录，保留最近 20 步。
3. **候选对比**：AI 候选在应用前，并排显示"新增 / 修改 / 删除"的差异摘要，不再只弹出 `window.confirm`。
4. **保存状态可见**：顶栏显示"已同步 / 保存中 / 离线·本地暂存"，同步失败时明确提示。
- 验收：
  - 新增 `check-recovery-transactions`：每个覆盖类动作都必须经过事务包装（静态扫描结合 mock 运行）；
  - 冒烟测试覆盖"应用候选 → 撤销 → 数据复原"。

### M2 可信：引用溯源贯通（2～3 轮，阶段 4 的延续）

1. 试点链路（OV-5 活动分解）经人工评审通过后，按价值顺序推广：作战任务 → 兵力编组 → OV-1 → 规则 → 想定。
2. **引用的三种状态**，在界面上用统一标记区分：
   - 有出处（可点开原文片段）；
   - AI 推断（无出处，明确标出）；
   - 人工编写。
3. **"证据覆盖率"指标**：每个产品显示"有出处的要素占比"，在评估页汇总。研究人员可以据此快速找到薄弱处。
4. **反向追溯**：在知识片段页能看到"它被哪些要素引用"。
5. **报告导出**：附上引用列表与脚注；可选生成 Obsidian 笔记回写（只新增笔记，绝不修改原笔记）。
- 验收：mock 测试覆盖合法引用、编造的引用、无引用三种情况；导出报告中的引用都能回链到片段。

### M3 好懂：降低上手门槛（约 2 轮）

1. **"下一步"导航**：每一步顶部只保留一个主按钮，同时说明"为什么做这一步、完成条件是什么"。完成条件就用现有门禁的判定结果，不另写一套逻辑。
2. **示例项目**：首次进入时可以一键载入一个完整的示例项目（已走完六步），作为参照和培训。
3. **术语悬浮说明**：OV-x、OODA 等术语统一维护一份词典（`shared/glossary.js`），在界面上悬停即可查看。
4. **信息减负**：
   - 每个视图默认只展示核心字段，高级字段折叠；
   - 动效统一受 `prefers-reduced-motion` 控制，并提供关闭开关；
   - 删除纯装饰性动画。
5. **空状态与错误文案**：所有空列表和失败提示都要给出"可以做什么"，不能只写"暂无数据"或原始错误信息。
6. **键盘与检索**：提供全局命令面板（Ctrl+K），可跳转视图、搜索要素、执行常用动作。
- 验收：
  - 找 3～5 名目标研究人员做可用性测试。首次使用、没有任何指导的情况下，在 30 分钟内用示例资料走完第 1～3 步；
  - 记录卡点并修复前 5 个。

### M4 AI 质量：可度量、可回归（约 1～2 轮，可与 M3 并行）

1. **黄金样例集**：`eval/cases/*.json` 收录 10～20 个典型输入，每个提示词 ID 至少 2 个样例。
2. **结构化校验**：所有 AI 输出先经过 schema 校验，再进入候选；校验失败时自动重试 1 次，仍失败就给出可读提示。
3. **评测脚本** `scripts/eval-prompts.mjs`：对比"提示词改动前后"的结构合法率、引用合法率和关键字段完整率。改提示词前后都要跑。
   - 这个脚本需要真实 AI，不进入日常的 `run-checks`。
4. **提示词版本**："AI 提示词"目录记录修改历史，可以回退。
5. **离线降级**：AI 不可用时，各生成按钮显示明确状态，并保留"手工起草 / 本地模板起草"路径。
- 验收：评测基线报告入库；任一提示词改动都必须附上前后对比。

### M5 研究闭环：评估与比较（约 2 轮）

1. **方案对比**：同一项目可派生多个方案分支（基于快照），并排比较关键差异与评估得分。
2. **红队审查增强**：每条红队意见都要关联到具体要素，并有"接受 / 驳回 / 已修订"状态。驳回需要填理由，结果进入报告。
3. **一致性检查可操作**：每个问题都提供"跳转并定位"（即修好后的 `jumpFromStructureReview`）；能一键修的问题给出修复建议。
4. **评审包**：一键导出评审材料，包括报告、引用、红队记录、未决问题清单。

### M6 工程可持续（贯穿各里程碑，每轮顺带推进一小步）

- 门槛：每次提交都必须保持 `run-checks` 全绿和冒烟测试通过，没有例外。
- `state` 的 144 个字段按领域分片（project / ui / ov1 / ov5 ...），每轮只迁一个领域，并配套 wiring 测试。
- 静态字符串断言型测试，在相关功能被改到时，逐步替换为行为断言。
- 数据安全：每日自动备份 `data/projects.sqlite`，保留 7 份；提供一键恢复（复用已有的备份脚本）。
- 性能预算：首屏小于 2 秒，视图切换小于 300 毫秒，由冒烟测试记录并告警。

## 3. 建议顺序

```text
M0 → M1 → M2(试点+推广前两条) → M3 ∥ M4 → M2(其余) → M5
                     M6 贯穿始终
```

理由：M1、M2 决定研究人员敢不敢用；M3 决定愿不愿意用；M5 是做深价值。

## 4. 不做清单（防跑偏）

- 不新增视图类型、不做大屏或驾驶舱风格、不新增装饰动效（至少到 M3 结束）。
- 不把概念图绘制作为开发重点（遵守 AGENTS.md）。
- 不换框架、不引入构建工具链，保持零依赖原生方案。
- 不改为 PostgreSQL 或 OIDC（仍属远期参考）。
- 不在一轮里同时推进两个以上里程碑。

## 5. 给执行代理的通用要求

1. 每个里程碑开工前，先写对应的执行计划（`plans/EXECUTION_PLAN_<日期>_<Mx>.md`），经人工确认后再动代码。
2. 每条结论都要附命令和输出；每个阶段单独提交。
3. 遇到数据结构或接口契约变更、修复范围超过约 300 行、或需要真实 AI 调用时，停下来报告。
4. 每个里程碑结束后，用 3～5 句话更新 `project-context.md` 的"当前状态"，不写长文。

## 6. 待人工确认的问题

- 目标用户是谁、典型任务是什么？M3 的可用性测试需要真实研究人员参与。
- 报告与评审包的格式要求，比如是否有单位模板？
- 知识库规模和敏感级别：影响检索方案和引用策略的严格程度。
