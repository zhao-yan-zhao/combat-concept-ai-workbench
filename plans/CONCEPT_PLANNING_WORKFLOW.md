# 作战概念规划流程调整计划

更新时间：2026-07-25  
状态：设计草案（未实现）  
范围：在「概念简报」之后插入完整的「作战概念规划」段，再进入 OV / OODA / 想定  
协作模式：**AI 主力生成，人工复核确认**（全流程默认，不限于规划段）

---

## 1. 问题与动机

### 1.1 现状

当前主流程大致是：

```text
简报 → 作战概念图 → OV-1 / OV-5 / OODA → 结构校核 → 推演评估 → 审阅交付
```

「作战概念图」阶段同时承担了过多职责：

- 兵力与任务还没讲清，就开始画图
- 阶段逻辑与转换条件没有独立确认
- 空间表达与总体概念表达混在一起
- 下游 OV 只能从一个混合产物里“抽取语义”

结果是：概念图既不够“规划”，又不够“正式建模”，人工确认点也容易散落。

### 1.2 调整目标

把简报之后的工作拆成一条**先定时序，再定人/事，再定空间，最后定总体概念**的规划链：

```text
简报
  → 作战概念规划
      1. 阶段与行动构想
      2. 兵力与任务设计
      3. 模糊作战图设计
      4. 作战概念图设计
  → OV-1 / OV-5 / OODA 等正式建模
```

核心原则：

1. **AI 主力、人工复核。** AI 负责起草、补全、汇总与跨步编译；人只做审阅、点改、质疑与确认，不以“从空白表单手填”为主路径。
2. **先语义，后图形；先抽象，后具象。**
3. **每一步只回答一个问题，并有明确复核门。** 未复核不得把该步语义当作下游权威输入。
4. **下游 OV 只消费已复核语义，不消费原始坐标/地图原始数据。**
5. **现有作战概念图能力由第 3、4 步继承，而不是推倒重做。**

### 1.3 协作模式（冻结）

整条研究链的默认分工：

| 角色 | 做什么 | 不做什么 |
|------|--------|----------|
| **AI（主力）** | 根据上游已确认结果生成完整草案；跨步编译；指出缺口与开放问题；在用户要求下重生成/局部改写 | 不绕过人工确认直接写死下游正式产物；不发明伪精确地理/性能 |
| **人（复核）** | 读草案、改关键字段、回答 AI 提出的开放问题、确认本步、驳回重生成 | 不要求从零手工搭完整兵力表/阶段树/概念图作为主路径 |

标准单步循环（四步规划及后续建模共用）：

```text
进入本步
  → AI 自动或一键生成完整草案（主路径）
  → 展示：草案正文 + 依据摘要 + 开放问题 + 与上游差异
  → 人工复核（可点改少量字段 / 要求 AI 按意见重写）
  → 确认本步（写入 confirmed + revision）
  → 解锁下一步；下一步 AI 默认读取本步确认结果继续生成
```

设计含义：

- **主按钮是“生成 / 按意见重生成”，不是“新建空条目”。** 手工增删条目是纠错手段，不是默认作业方式。
- **确认 = 对人机共同结果负责**，不是“人已经手写了一遍”。
- 若用户几乎不改就确认，流程应流畅；若频繁驳回，AI 应带着批注重写，而不是逼人改表格。
- 测试/解锁模式可浏览未确认步骤，但**不得把未确认草案伪装成已复核权威输入**。

## 2. 思维整理：这条规划链在回答什么

| 步骤 | 要回答的核心问题 | AI 主力产出 | 人工复核重点 | 不在本步解决 |
|------|------------------|------------|--------------|--------------|
| 1 阶段与行动构想 | 先做什么、后做什么、何时转换 | 完整阶段链、主次行动、转换条件、阶段效果 | 阶段逻辑与转换条件是否成立 | 兵力编组细节、地图几何 |
| 2 兵力与任务设计 | 谁参与、谁负责什么 | 完整编组、角色、任务、指挥/保障关系草案 | 完整性、合理性、职责边界；批注后可令 AI 重写 | 空间部署、正式 OV 图元 |
| 3 模糊作战图设计 | 空间关系是否说得通 | 抽象区域、群组相对落位、方向、阶段覆盖、关键关系 | 空间关系是否符合构想；是否误当真实部署 | 精确坐标、军标细节、正式 OV-1 成图 |
| 4 作战概念图设计 | 总体构想是否完整可表达 | 汇总任务/兵力/指挥/关键行动/预期效果的总体图与叙述 | 是否足以支撑正式 OV-1；与前三步是否一致 | 下游活动细拆、OODA 行为细节 |

一句话串起来：

> **AI 依次起草“按什么顺序做 → 谁做什么 → 空间上是否说得通 → 总体构想图”，人在每步复核确认后放行；再交给 OV 体系做正式建模（同样 AI 起草、人工复核）。**

## 3. 目标流程

### 3.1 目标主流程

```text
研究准备
  └─ 概念简报（意图、目标、假设、效果、风险、证据）

作战概念规划（新增主段）
  ├─ 1 阶段与行动构想
  ├─ 2 兵力与任务设计
  ├─ 3 模糊作战图设计
  └─ 4 作战概念图设计

概念建模
  ├─ OV-1（由第 4 步正式形成）
  ├─ OV-5 / OODA
  └─ …

结构校核 / 推演评估 / 审阅交付
  （沿用现有能力）
```

### 3.2 与现有阶段门禁的对应关系（建议）

| 现有阶段索引 | 现有含义 | 调整建议 |
|-------------|---------|----------|
| 0 | 研究准备 / 简报 | 保持 |
| 1 | 作战概念图（单阶段） | **拆成「作战概念规划」段**，内部 4 步串行确认 |
| 2 | 概念建模 OV-1/OV-5/OODA | 保持；输入改为“已确认的规划产物” |
| 3+ | 结构校核 / 推演 / 交付 | 保持 |

实现上可以二选一（实施前再定）：

- **方案 A（推荐）**：门禁仍按“大阶段”走，`作战概念规划` 作为阶段 1；内部 4 步是子阶段（`subStage`），全部确认后才 `completedThrough >= 1`。
- **方案 B**：把 4 步都抬成独立 workflow stage，门禁更细，但会显著拉长确认链和失效传播。

首版建议 **方案 A**：用户感知到 4 步，系统门禁只多一个“规划完成”总确认。

## 4. 四步产品定义

### 4.1 步骤 1：阶段与行动构想

**输入**

- 已确认简报（目标、思路、假设、效果、风险）
- 可选：已选知识证据（仅研究级摘要，不含敏感原文）

**AI 生成内容**

- 阶段划分与阶段目标
- 各阶段主次行动
- 阶段转换条件
- 阶段预期效果
- （兵力挂接后置，本步不强制）

**人工复核重点（非主填）**

- 阶段顺序是否合理
- 转换条件是否可观察、可判断
- 主次行动是否覆盖简报目标
- 阶段划分是否足以支撑后续兵力设计
- AI 应自动跑一遍上述一致性检查，把问题放进 `openQuestions` / `reviewChecklist`，人只裁决

**默认交互**

1. 简报确认后 → 主路径「根据简报生成阶段与行动草案」
2. 时间线主轴 + 单阶段深读复核；可批注重生成
3. 确认后自动进入步骤 2（兵力与任务）

**产出对象**

- `phaseActionConcept`

**界面设计（已实现）**

- 顶部简报依据条（目标/思路/效果/风险）
- 横向阶段时间线（点选聚焦）
- 左：当前阶段目标、主次行动、进出条件
- 右：转换条件 + 复核清单/开放问题/批注

---

### 4.2 步骤 2：兵力与任务设计

**输入**

- 已确认简报
- 已确认 `phaseActionConcept`（主路径）
- 可选：已选知识证据

**AI 生成内容**

- 兵力编组（概念级，非编制表）
- 能力角色（感知 / 指挥 / 行动 / 保障 / 外部 等受控角色集）
- 任务分配（谁承担什么概念任务）
- 指挥 / 保障关系（高层关系，不是真实机构人事）

**人工复核重点（非主填）**

- “谁负责什么”是否完整
- 是否缺关键角色或重复职责
- 指挥与保障关系是否自洽
- 是否覆盖各阶段主行动的责任主体

**默认交互**

1. 步骤 1 确认后 → 主路径「根据阶段与简报生成兵力与任务草案」
2. 人工浏览列表/关系；可批注重生成
3. 确认后放行步骤 3（模糊作战图）

**产出对象（建议资源名）**

- `forceMissionPlan`

**建议最小数据结构**

```text
phaseActionConcept
  version
  status: empty | draft | confirmed
  generation: { source: ai|manual-edit, model, generatedAt, promptSummary, reviewNotes }
  phases[]: {
    id, name, objective,
    primaryActions[], secondaryActions[],
    entryConditions[], exitConditions[],
    expectedEffects[], forceIds[]
  }
  transitions[]: { fromPhaseId, toPhaseId, condition, note }
  openQuestions[]
  reviewChecklist[]
  sourceForceMissionRevision
```

**后续 OV 衔接**

| 本步语义 | 下游用途 |
|----------|----------|
| phases 层级 | OV-5a 分解树骨架 |
| actions | OV-5b 活动骨架 |
| entry/exit conditions | OV-6a 规则候选；OV-6b 状态候选 |
| transitions / 事件序 | OV-6c 事件序列骨架 |

说明：本步**不直接落正式 OV 产品**，只产出“AI 起草、人工复核后的语义骨架”；正式 OV 仍由后续建模段 AI 再生成、人再复核。

---

### 4.3 步骤 3：模糊作战图设计

**定位**

- 研究级、抽象相对布局的空间语义检查
- **不是**精确部署图，也不是最终 OV-1 成图
- 继承并收敛现有 `conceptMap` 中“初图 + 相对布局 + OV reference”能力

**输入**

- 已确认 `forceMissionPlan`
- 已确认 `phaseActionConcept`

**AI 生成内容**

- 抽象区域（任务区、关注区、通道、屏障等研究级区域）
- 兵力群组在相对方位上的落位（slot / 相对关系，非真实坐标主张）
- 主要方向与阶段覆盖
- 关键空间关系（相邻、对向、支援距离感、通道控制等文字/关系表达）

**人工复核重点（非主填）**

- 空间关系是否符合阶段与任务构想
- 群组相对位置是否说得通
- 阶段覆盖是否完整
- 是否误把抽象图当成真实地理部署
- 外部地图工具仅作**可选精修**，不是默认必经；默认应在工作台内看懂 AI 草案并确认

**默认交互**

1. 步骤 2 确认后 → 主路径「根据阶段构想生成模糊作战图」
2. 工作台展示相对布局摘要 + 空间语义参考；人复核后确认
3. 可选：导出 JSON 到独立工具修订再回传（旁路，非主路径）

**产出对象**

- `fuzzyConceptMap`（可由现有 `conceptMap` 资源演进/拆分）

**数据边界（硬约束）**

允许进入下游的：

- 区域名称与语义角色
- 兵力群组与相对方位描述
- 高层空间关系
- 阶段覆盖说明
- **人工复核确认后**的 OV 参考摘要

禁止进入下游的：

- 原始经纬度 / 相机参数
- 地图编辑器原始 items 全量
- CMO 军标文件名等工具私有字段
- 任何“看似精确”的性能或航路细节

**后续衔接**

- 为 OV-1 提供空间语义（谁在什么概念区域、方向关系）
- 为想定提供空间语义骨架
- **不**直接写 OV 原始图元坐标

**与现有能力继承**

| 现有 `conceptMap` 能力 | 落到本步 |
|------------------------|----------|
| `ConceptMapInitialPlan`（forces/areas/relations/phases） | 作为模糊图 AI 合同基础，输入改为步骤 1+2 **已复核**结果 |
| `abstract-relative-layout` | 保留，作为唯一空间模式 |
| `reference`（entities/relations/activities…） | AI 产出草案 → 人工复核确认 |
| JSON 导出到独立地图工具 | 可选精修旁路；默认不要求离开工作台 |
| 下游 `conceptMapContextForDownstream` | 只读已复核确认的模糊图语义摘要 |

---

### 4.4 步骤 4：作战概念图设计

**定位**

- 汇总前三步，形成**总体作战构想**表达
- 正式成为 OV-1 的直接来源
- 同时为 OV-5b、OODA 提供已确认的总体语义

**输入**

- 已确认步骤 1～3 全部产物
- 简报

**AI 生成内容**

- 总体概念叙述
- 关键实体与关系汇总（任务、兵力、指挥、关键行动、预期效果）
- OV-1 候选节点/边（研究级）
- 活动候选与 OODA 关注点提示
- 仍存疑的开放问题

**人工复核重点（非主填）**

- 是否完整表达总体作战构想
- 与前三步是否一致（无静默漂移）——**一致性由 AI/编译器先自检，人只看差异报告**
- 是否达到“可以进入正式 OV 建模”的成熟度

**默认交互**

1. 步骤 3 确认后 → 主路径「汇总生成总体作战概念图」
2. AI 汇总前三步 + 简报，产出叙述、节点/边、活动候选、开放问题
3. 人复核通过后确认 → AI 再生成正式 OV-1 草案（进入概念建模段）

**产出对象**

- `operationalConceptGraphic` / 强化后的 OV-1 输入包
- 或：在现有 `ov1` 资源前增加 `conceptGraphicPlan`，确认后由 AI 种子化 OV-1

**建议最小数据结构**

```text
conceptGraphicPlan
  version
  status: empty | draft | confirmed
  generation: { source: ai|manual-edit, model, generatedAt, promptSummary, reviewNotes }
  narrative
  nodes[]: { id, label, role, fromForceIds[], fromPhaseIds[], note }
  edges[]: { id, from, to, type, note }
  effects[]
  activityCandidates[]
  oodaHints[]
  openQuestions[]
  consistencyReport[]   # 与步骤 1～3 的对齐检查结果，供人复核
  lineage: { forceMissionRevision, phaseActionRevision, fuzzyMapRevision, briefRevision }
```
**后续 OV 衔接**

| 本步语义 | 下游用途 |
|----------|----------|
| nodes/edges | **正式形成 OV-1** |
| activityCandidates | OV-5b 直接来源之一 |
| oodaHints | OODA 初始关注点 |
| effects | 与简报 expectedEffects 对齐，进入效果评估节点 |

## 5. 数据流与继承关系

### 5.1 语义传递（允许）

```text
brief
  → forceMissionPlan
      → phaseActionConcept
          → fuzzyConceptMap.reference / spatialSemantics
              → conceptGraphicPlan
                  → OV-1（正式）
                  → OV-5 / OODA（种子）
```

### 5.2 不传递（禁止）

```text
fuzzy map raw document.items
  坐标 / 相机 / CMO 文件名 / 编辑器私有状态
    ✗ 不得进入 OV-1 / OV-5 / OODA / 报告正文
```

### 5.3 现有“作战概念图”如何继承

不要理解为“删除 concept-map 页面”，而应理解为**职责拆分**：

| 旧职责（单页 concept-map） | 新归属 |
|----------------------------|--------|
| 从简报直接猜兵力/阶段/区域 | 步骤 1 + 2 显式完成 |
| 抽象相对布局初图 | 步骤 3 模糊作战图 |
| OV reference 确认 | 步骤 3 草案 → 步骤 4 汇总确认 |
| 作为 OV-1/OV-5 上游上下文 | 步骤 4 确认后的总体概念图 |
| 独立地图工具 JSON 交接 | 主要挂在步骤 3；步骤 4 可只读引用其确认摘要 |

迁移策略（实现时）：

1. 保留 `conceptMap` 资源与验收脚本骨架，避免一次性大爆炸。
2. 将 `draft.plan` 中混杂的 forces/phases/areas 拆到步骤 1/2/3 资源。
3. `conceptMap.reference` 升级为“由前序确认结果编译 + 人工修订”，而不是从简报一次生成。
4. 旧项目数据：若仅有旧 conceptMap，可在加载时标记为“待迁移/待拆分”，不自动假装已完成 1～2 步。

## 6. 复核门禁与失效规则

### 6.1 AI 主路径 + 复核顺序

```text
简报（AI 草案 → 人复核确认）
  → 步骤1 AI 生成 → 人复核确认
    → 步骤2 AI 生成 → 人复核确认
      → 步骤3 AI 生成 → 人复核确认
        → 步骤4 AI 汇总 → 人复核确认
          → 解锁概念建模
            → OV-1 / OV-5 / OODA 仍为 AI 生成 + 人复核
```

可选加速（二期，不降低复核责任）：

- **连续推进**：确认本步后自动触发下一步 AI 生成，人连续复核
- **批注重写**：人只写短意见，AI 局部或整步重生成，避免手改大表
- **差异高亮**：重生成后只标与上一草案/上游确认结果的差异，降低复核成本

### 6.2 内容变更失效（建议）

| 被改资源 | 失效范围 |
|----------|----------|
| brief | 步骤 1～4 及之后全部（与现网一致的“上游失效”） |
| forceMissionPlan | 步骤 2～4 + 概念建模及之后 |
| phaseActionConcept | 步骤 3～4 + 概念建模及之后 |
| fuzzyConceptMap | 步骤 4 + 依赖空间语义的下游 |
| conceptGraphicPlan / 已确认总体概念 | OV-1/OV-5/OODA 及之后 |

原则与现网 `workflowConfirmation` 一致，并叠加 AI 主路径语义：

- 真实内容变更撤销本阶段及后续确认；后续步骤标记为 `stale`，**默认由 AI 按新上游重生成草案**，而不是要求人手工同步
- 幂等保存不撤销
- 人工可在测试/解锁模式下跳过浏览限制，但不伪造“已复核确认”
- AI 重生成会把 status 从 `confirmed` 拉回 `draft`（若改的是本步）或使下游 `stale`

### 6.3 每步完成判据（首版）

完成 = **AI 已产出合格草案 + 人已确认**，不是“人已手填齐全”。

| 步骤 | 最少完成条件 |
|------|----------------|
| 1 | 存在 AI/有效草案：≥1 个 force；每个 force 有 role+task；至少 1 条关系或明确“无指挥链”说明；status=confirmed |
| 2 | ≥2 个 phase；每 phase 有 objective + 至少 1 主行动；相邻 phase 有 transition/exit condition；status=confirmed |
| 3 | 有抽象区域或群组相对布局摘要；OV 空间参考已人工复核；无“伪精确坐标”声明；status=confirmed |
| 4 | nodes/edges 覆盖兵力、指挥、关键行动、效果；consistencyReport 无阻断项或人已明示接受；status=confirmed |

## 8. 界面与导航建议（克制、研究工具化、AI 主路径）

### 8.1 导航结构

在「研究建模」轨中，简报后增加分组：

```text
研究建模
  ├─ 概念简报
  ├─ 作战概念规划          ← 分组标题（非独立编辑页）
  │    ├─ 兵力与任务
  │    ├─ 阶段与行动
  │    ├─ 模糊作战图
  │    └─ 作战概念图
  ├─ OV-1
  ├─ OV-5b
  └─ OODA
```

交互原则：

- 每步一页，左侧步骤条显示 1/2/3/4 与状态：`待生成 | 草案待复核 | 已确认 | 已过期`
- **页面首屏是草案阅读与复核区**，不是空白表单墙
- 主操作区固定：`生成/重生成` · `按批注改写` · `确认本步`；次要：`点改字段` · `导出/旁路工具`
- 右侧 inspector：本步对象摘要、上游依据、AI 开放问题、一致性提示；不堆知识库全文
- 模糊作战图页可继续“全宽工具区”；其余三步以**可读草案卡片 + 轻量关系图 + 少量点改**为主
- 不做大屏态势、不做炫技动画

### 8.2 AI 动作命名（建议）

| 步骤 | 主按钮（AI 主力） | 复核按钮 |
|------|-------------------|----------|
| 1 | 根据简报生成兵力与任务草案 | 确认兵力与任务 |
| 2 | 根据兵力任务生成阶段与行动草案 | 确认阶段与行动 |
| 3 | 根据阶段构想生成模糊作战图 | 确认模糊作战图 |
| 4 | 汇总生成总体作战概念图 | 确认总体概念图 |

每步另有：

- **按批注重生成**（主纠错路径）
- **从上游重新编译**（上游变更后默认建议）
- 点改单字段 / 增删条目（次要纠错）
- 可选字段锁定（二期：重生成时保留人改过的关键项）

## 11. 风险与边界

| 风险 | 缓解 |
|------|------|
| 四步过重，用户觉得流程变长 | AI 出完整草案 + 一键确认；确认后可自动生成下一步；测试模式可跳览 |
| 人变成“点确认机器” | AI 必须给出 openQuestions / 一致性报告 / 与上游差异，复核有信息量 |
| 与现有 conceptMap / OV-1 双重来源冲突 | 单一权威：已复核步骤 4 → AI 形成 OV-1 |
| AI 在步骤 3 发明伪精确地理 | 合同与编译器强制 abstract-relative-layout；验收禁止真实坐标主张 |
| 失效链过长导致反复重做 | 上游变更后下游标 stale，默认 AI 重生成；字段锁定二期 |
| 独立地图工具边界被再次打穿 | 继续禁止工作台管理/注入 combat-map-web；仅用户管理的 JSON 交接 |
| 无网/无密钥时卡死 | 保留 mock generator，仍走“草案→复核”同一 UX |

## 12. 成功标准（验收口径）

1. 简报确认后，用户以 **AI 生成 → 复核 → 确认** 依次完成四步，而不是从空白表单手搭规划。
2. 任一步无草案或未复核时，正式概念建模入口给出明确缺失原因。
3. OV-1 可由步骤 4 已复核结果经 AI 形成，且能追溯到步骤 1～3 revision。
4. OV-5a/5b、OV-6* 候选能说明来自阶段与行动构想，而不是凭空生成。
5. 任何下游 API/AI 上下文都不包含模糊图原始坐标或编辑器私有载荷。
6. 每步 UI 主路径包含生成/重生成与确认；手工编辑仅为次要纠错且可测。
7. 现有 concept-map 集成测试可演进通过，不破坏“独立地图工具”边界。
8. 全量检查脚本与 `/api/health`（sqlite 仓储）通过。
